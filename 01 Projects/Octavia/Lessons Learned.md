# Lessons Learned

The expensive ones, so we never pay twice. (VAD specifics live in [[Silero VAD Context Window]]; model choice in [[Choosing a Local Model]].)

## Machine learning runtimes

- **Silero VAD returns a flat 0.0 for everything unless each 512-sample frame is prefixed with the previous frame's last 64 samples.** No error, no warning — just confident silence on obvious speech. The official Python wrapper does this invisibly, so every port that reads only the ONNX signature gets it wrong. Cost an hour; found by probing the raw model with and without context side by side. See [[Silero VAD Context Window]].
- **Whisper.net reports `Probability` as 0.00 unless the processor is built with `.WithProbabilities()`.** A confidence gate silently rejecting everything looks exactly like a broken recognizer.
- **Whisper hallucinates fluent text out of silence.** Three seconds of digital silence produced `[BLANK_AUDIO]`; noise produces "Thank you." or subtitle credits. A VAD in front is not an optimisation, it is the thing that makes Whisper usable. Filter bracketed non-speech tags as a second line of defence.
- **whisper.cpp's native teardown corrupts the process exit code.** A test harness that returned normally reported exit -1 with every check passing. `Environment.Exit(n)` instead of `return n`.

## Streaming text

- **A lookahead filter must not hold back a fixed margin.** The `<think>` filter held 6 characters (the length of the tag minus one) so it could detect a tag split across chunks — which meant any reply *shorter than the tag* was held entirely, never counted as spoken, and `LocalBrain` threw "returned nothing". Only reproduced on short replies, which is exactly what her persona asks for. Hold back only a genuine **prefix of the tag**, and count whatever the filter flushes as real output.
- **Small reasoning models narrate their scratchpad inline.** Without filtering, `<think>…</think>` gets read aloud. The tags arrive split across SSE chunks (`<thi` then `nk>`), so the filter has to be a state machine, not a regex.
- **Sentence splitting must know that `3.50` is not two sentences.** Otherwise she says "It costs three point" and then "fifty today."

## Audio and devices

- **A capture device can open successfully and deliver pure digital silence.** Over RDP the microphone appears as "Remote Audio", is correctly the Windows default, and NAudio opens it without error — while the client forwards nothing because *"Record from this computer"* is off by default and only negotiated at connection time. Windows' own `AudioMeterInformation.MasterPeakValue` reads 0.000, which is what separates "no audio arriving" from "our capture is misconfigured". **Diagnose upstream of your own code first.**
- **Silence must be reported, not just handled.** She sat looking like she was listening and never answered — the worst possible failure mode. There is now a watchdog: mic open, zero signal for 10 seconds, say so on her face. Distinguish digital silence (exactly 0.0) from a quiet room (always has a noise floor) or it cries wolf.
- **NAudio 3.x renamed `WaveInEvent` to `WaveIn`** — but the event args type is still `WaveInEventArgs`. A blind rename breaks the build in a confusing way.

## Choosing models

- **Tokens per second is the wrong metric for a talking avatar.** `qwen3:1.7b` ran 2.5× faster per token than `llama3.2:3b` and was still **slower to finish**, because it ignored "two or three short sentences" and emitted 145 tokens against llama's 38. Wall clock is what the user feels. Judge on **tokens emitted**, and measure on the actual target machine.
- **A 4B model will not hold a persona.** Expect markdown, rambling and stage directions no matter how firm the system prompt. It is a test of the *pipeline*, not of her character — say so up front or the dev build reads as a regression.

## Platform

- **The `net10.0-windows` TFM alone rejects `SupportedOSPlatformVersion`.** Put the version in the TFM itself: `net10.0-windows10.0.19041.0`.
- **The WindowsDesktop implicit-using set omits `System.IO` and `System.Net.Http`**, unlike the plain SDK. Add them as `<Using>` items rather than sprinkling usings.
- **`System.Text.Json` escapes `+` to `+` by default**, which makes a hand-editable config file look corrupted (`"Ctrl+Alt+O"`). `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` for anything a human will read. **This bit twice** — the second time in the diagnostics bundle's redacted config copy, written with a fresh options object that did not carry the encoder. The rule is not "set it once"; it is *every* serializer whose output a person opens.
- **`Ctrl+Alt+Space` is commonly owned by an IME** and `RegisterHotKey` fails with 1409. Make the hotkey configurable and log the actual Win32 error, or it looks like your code is broken.
- **Killing a process and immediately relaunching races the single-instance mutex.** The second instance saw the mutex still held and exited — which read as a bad build. Wait for teardown before concluding anything.
- **A second instance should surface the first, not exit silently.** Double-clicking the exe while she sits in the tray appeared to do nothing at all.

## Asynchrony and threads

- **A discarded task swallows its exception until the garbage collector notices.** `_ = SomeAsync()` is how a subsystem stops working without saying anything: the "Save diagnostics" button threw on every press and produced no dialog, no error, no log line. Every fire-and-forget now goes through a `Forget(what)` helper that logs the fault where it happens.
- **A file dialog must be *constructed* on the UI thread, not merely shown there.** Building `SaveFileDialog` on a socket thread and then marshalling `ShowDialog()` throws on the constructor. Marshal the whole operation, not the last line of it.
- **`.GetAwaiter().GetResult()` on the dispatcher thread deadlocks** any task whose continuations post back to that thread. The headless `--diagnostics` command hung forever with no window and no output — worse than failing. `Task.Run(...)` first to escape the synchronisation context.
- **A flag that guards *ingest* must never be applied to work already in flight.** `_muted` and `_wantListening` exist to stop her transcribing the room. `TranscribeAsync` checked them when it *finished* — and `ReleaseFloor` flushes to Whisper and then calls `Stop()` on the very next line, which clears `_wantListening`. So every push-to-talk utterance from a room was transcribed and silently discarded a second later. It worked at the desk only because `_wantsToListen` is true there and `Stop` is never reached. **Nothing spoken into a phone had ever reached her, for twenty-six versions.** Decide at the point the work is *accepted*; a flag read at completion is answering a different question than the one you asked.
- **Transcription outlives the press, so anything the words need must be latched, not read later.** `talking:false` clears the floor synchronously; Whisper answers seconds afterwards. `EarsRoom` therefore said "host" by the time the sentence existed, and a phone's words were judged by the *desktop's* attention gate and answered in the desktop's room. Latch the speaker at flush time and read it once. The same applies to any "who/where/why" a late callback will need.
- **The pattern behind all of these:** the bug was invisible, and each was found by testing the *user-facing path* rather than the unit. The harness proved the bundle writer; only pressing the button proved the button.

## Configuration

- **A fix built on a hand-kept list is a bug with a delay on it.** The v0.4.1 flattening fix carried *named* properties (`VoiceName`, `VoiceRate`) back to the un-overlaid settings. Two versions later a settings menu added `AvatarFile` and `RoomHour`, which reached the host, changed the face, wrote a log line — and were silently dropped on save. The list had no way to know. Comparing against **the settings as they stood at load** gives the same guarantee and cannot fall behind, because "what changed while running" is computed, not remembered.
- **Test that a setting persists, not that it applies.** Everything about the settings menu looked right: the dropdown, the log line, the face changing. Only reading `config.json` afterwards showed nothing had been saved.
- **A config object that is loaded merged must not be saved merged.** Profile overlays were applied in memory and the design said `Save()` would never write them back — but `Save()` simply serialised `this`, and `this` *was* the merged copy. One voice change on the `dev` profile baked `Brain: local` into the base settings, and from then on the profiles were decoration. The invariant was documented in a comment and never tested, which is the whole failure. Keep a reference to the un-overlaid original and write **that**.
- **A Windows shortcut can pass an argument but cannot set an environment variable.** Selecting a profile by env var and config key only meant a launcher had no way to state its own intent — so which brain the desktop icon opened depended on a mutable file the app itself rewrites. Anything a launcher must pin needs a command-line form.
- **Say where a setting came from, not just what it is.** `profile 'dev'` in the log cannot distinguish "the shortcut asked for this" from "the file happened to say so", which is precisely the question when the wrong brain starts. `profile 'dev' (command line)` answers it in one line.
- **Make the current profile visible where the app is.** Tray tooltip and status panel, not only the log — the person who notices the wrong model is looking at her face, not at `%APPDATA%`.

## Audio and DSP

- **Do not build on a capability the next engine will not have.** The plan for the neural voice assumed phoneme timings from the engine. Piper hands over a waveform and nothing else, and so will most of its replacements. Deriving the mouth from the *audio* instead is less precise and completely portable — and it is the same DSP the music stage needs.
- **Speech tilts downward at ~6 dB/octave, so raw band energies always favour the low band.** Before compensating, 63% of voiced frames read as the same rounded vowel. Weight the bins by frequency before comparing bands.
- **A threshold tuned on one voice is a threshold that only works on one voice.** Fixed cut-points calibrated on Piper made SAPI mumble in a single shape. Track a running centre and express the boundaries as multiples of it; both engines then use their whole range.
- **Analyse at playback, not at generation.** Synthesis runs ahead of the sound card once warm, so a mouth driven from the generator finishes the sentence a second before it is heard. Tap the stream between the buffer and the output device.
- **"Nothing has arrived" and "nothing is coming" look identical.** An end-of-utterance watchdog that only checks for quiet fires *during* synthesis, before the first sample exists — she went idle and then started talking. Wait for the beginning before you are allowed to detect the end.
- **A sound card is fed continuously; an empty buffer comes back as silence.** Analysing that produced a viseme twelve times a second forever, each one saying "mouth shut". Send on change, not on tick.
- **Judge lip sync with a probe, not an assertion.** `EarsTest -- mouth <wav>` prints the shape timeline and the distribution behind it. Assertions can only pin the properties; whether it looks like talking is a thing you have to be able to *look at*.
- **Measure how good the audio is before doubting the arithmetic.** The tempo would not settle live while locking to 0.3 bpm offline, and every symptom pointed at the analyser. It was the *path*: Remote Desktop's audio endpoint normalises everything to full scale — **crest factor 1.7**, near square — and a beat cannot be found in audio with no dynamics left in it. What settled it was two numbers: delivery was 99.8% complete, and playing at a **quarter** of the volume returned byte-identical statistics. A signal-quality measure belongs beside the frame count in any capture diagnostic; "we received everything" and "what we received is usable" are different claims.
- **Integer-lag autocorrelation is biased, and unevenly.** A tempo is rarely a whole number of analysis hops — 150 bpm is exactly 37.5 — so correlating at the nearest integer understates that peak while a bar line landing on a whole number scores in full. The result was a track reading at exactly half speed. Interpolate the peak parabolically.
- **A test signal can be wrong in a way that looks like a bug.** The first synthetic kick drum was a pure 55 Hz sine, which occupies about one FFT bin and barely registers in spectral flux — so only the backbeat was visible and a 150 bpm track genuinely *was* 75 bpm of onsets. Real kicks have a beater click. When a detector fails on synthetic material, ask whether the material is real before changing the detector.
- **Set a threshold from a measured distribution, and check it has a sign.** The octave-preference cut-off sits at 0.45 because doubling-is-right scores 0.63–0.67 and doubling-is-wrong scores about −0.03. Two clusters that far apart, on opposite sides of zero, make a single constant defensible; a number chosen because it made the test pass would not have been.
- **She hears herself.** Anything she says comes out of the speakers and back through the loopback. The instinct is to stop analysing while she speaks, but that loses the beat of a track she is talking over — *hold the decision and keep the clock running* instead. Any machine that both listens and speaks has this problem.

## Rendering

- **`smoothstep` with its edges reversed is undefined in GLSL**, and the symptom is not an error — it is the effect silently not happening. `smoothstep(1.05, 0.18, d)` for an inverted ramp compiled and ran and drew no vignette at all. Write `1.0 - smoothstep(0.18, 1.05, d)`.
- **A backdrop plane always finds a window shape where its edges show.** Sizing it "generously" only moves the problem: too large and the gradient and vignette happen off-screen, which looks exactly like having neither. A fullscreen quad drawn before the scene has no edges, needs no aspect guessing, and is cheaper.
- **three.js ships as more than one file since r160-ish.** `three.module.js` imports `three.core.js`; vendoring only the first gives a 404 that surfaces as "the scene did not build". Check the module's own imports after downloading, not just its name.
- **three has no UMD build any more.** Moving to r158+ for `@pixiv/three-vrm` means module scripts, which changes execution order: classic scripts run at parse, modules run deferred and in document order. A classic `bridge.js` reading `window.Face` from a module `face.js` sees `undefined` and reports the renderer as broken.
- **Every VRM is authored in a T-pose.** The format defines a rest position, not an idle, so a freshly loaded character stands with her arms straight out. Posing the upper arms down on load is not a nicety; it is the difference between a character and a mannequin.
- **Frame the camera to the character, not the character to the camera.** Scaling a person to fit a bust's framing distorts them; reading the head bone's world position and placing the camera relative to *that* makes a tall character and a short one the same size on screen.
- **Pick your vocabulary from the thing you are going to integrate with.** Naming the expression set after VRM 1.0's presets (`happy/angry/sad/relaxed/surprised/neutral`, visemes `aa/ih/ou/ee/oh`) meant the protocol mapped onto a real character by identity. A vocabulary invented first would have needed a translation table, and translation tables are where this kind of thing rots.
- **Anything that hides a sibling of the canvas re-frames the camera.** The caption was collapsed to give her more room; collapsing it grew the stage by 92px, the `ResizeObserver` fired, the fit and camera distance were recomputed, and she visibly jumped size twice a cycle. The feature meant to give her the room was the thing moving her. Chrome that comes and goes over a 3D view belongs **inside** the view as an overlay, not above or below it in the flow — then only opacity animates and the viewport is a constant.

## Sockets and protocols

- **Loopback is "potentially trustworthy", so `ws://127.0.0.1` is reachable from an `https` page.** Mixed-content blocking does not apply. Worth knowing before designing around a limit that is not there — it let the built-in face and external faces share one transport instead of two.
- **Cancelling a `ReceiveAsync` ABORTS a WebSocket**, it does not time out. A per-read timeout in a polling loop kills the connection on the first quiet moment, and the socket can then no longer be closed politely. Use one long-lived token for the session.
- **Reproduce the bug before fixing it, even when the report is detailed and from someone competent.** A specification opened with a concurrency fault described precisely: `SendAsync` rejects overlapping sends, the catch-all swallows it, a live face is dropped silently. Every part of that reasoning was sound and the conclusion was wrong for this runtime — .NET serialises concurrent sends behind a lock, measured at 320 overlapping calls with nothing thrown. The tell was a test written against the stated failure **passing against the unfixed code**, twice. The right response to a check that will not go red is to doubt the premise, not to hunt for a harder reproduction. (The fix was still needed, for the fault next door: un-awaited sends to a face that stopped reading never complete and accumulate without bound.)
- **Asserting a silence is the one test that needs a timeout, and a timeout is exactly what a WebSocket cannot have.** Proving that a face which was *not* addressed received nothing means waiting for a message that should never come — and the obvious `CancellationTokenSource(1s)` around `ReceiveAsync` **aborted the very connection the test was proving had been left alone**, so the next check reported it as departed. Race the read against `Task.Delay` instead and leave it pending. The rule two bullets down had been written for months and still caught the person who wrote it; a lesson recorded is not a lesson remembered at the moment it applies.
- **A credential path nothing has ever walked is not working code; it is unwritten code that happens to compile.** The remote key could never authenticate anybody from v0.14.0 to v0.23.1 — the reader required 24 characters, the writer made 23, so every read of the key discarded it and minted a new one, and the offered key was compared against a secret one microsecond old. Nine versions of nobody noticing, because the phone reached her over `adb reverse`, which is loopback, which uses the token. That branch was reviewed, documented in two places and reasoned about at length; none of that is evidence. The first connection over WiFi broke it on the first try. **Ask which paths the tests actually traverse, not which ones look covered.**
- **Answer a close frame.** A server that just drops the socket leaves a client that disconnected politely staring at "closed without completing the close handshake". Found by the protocol test, not by the app.
- **`HttpListener` needs a urlacl reservation** outside the default namespace — meaning elevation or a setup step. `TcpListener` + `WebSocket.CreateFromStream` avoids that entirely and still lets the framework do the framing.

## Environment and tooling

- **The Store/MSIX PowerShell 7 has a virtualized view of AppData.** `winget install Microsoft.PowerShell` as an unelevated user installs the MSIX package, whose `pwsh.exe` genuinely **cannot see** `%APPDATA%\Octavia\octavia.log` — `Test-Path` returns false for a file that plainly exists. It fails silently and looks like a bug in your script. Use the plain ZIP release extracted to `%LOCALAPPDATA%\Programs\PowerShell7` instead; no installer, no elevation.
- **An admin account running unelevated has a *filtered* token.** `IsInRole(Administrator)` is false **and** the token's group list omits Administrators — those are one fact, not two. Never report "not in the admin group" from a token check; read `net localgroup Administrators` for actual membership. Conflating them produced a confidently wrong statement.
- **Quoting does not survive nesting.** Backtick escapes passed through Bash into `pwsh -Command`, and `$`-escapes through 5.1, both corrupt the script silently — twice producing a literal `n` where a newline belonged, and once turning a heredoc's apostrophes into a parse error. Use `-File <script>` or the editor tools. This has now cost time in three separate sessions; treat any nested-quoting attempt as the wrong approach rather than one to get right.
- **An obsolete API's replacement will tell you its own rules, one at a time.** `WasapiLoopbackCapture` is deprecated in favour of `WasapiRecorderBuilder`, which then refused three configurations in a row — routing needs `BuildAsync`, routing cannot combine with `WithDevice`, routing follows the *capture* device and cannot combine with loopback at all. Every message was accurate and actionable. Read them and adjust rather than reverting to the deprecated call; the end state was better than the one first attempted, and the constraint learned last is now a comment in the file.
- **`requestAnimationFrame` does not run in a hidden tab.** Measuring an animation through an automated browser whose pane is not displayed returns **zero frames per second**, so every value driven by the render loop reads as its initial state and the code looks broken. Screenshots still work, because capture forces a paint — which is what makes it convincing. Check `document.hidden` before believing a timing measurement.
- **A frozen CSS transition reports a settled-looking value that is neither end of it.** The same hidden pane stops transitions mid-flight, so an element fading from 1 to 0 sat at `opacity: 0.65` and stayed there across repeated reads. That reads exactly like a rule being overridden by a more specific one, and sent a real fix down a cascade rabbit hole. To test a cascade, set `transition: none`, toggle the class, and read the two states — an answer that does not depend on anything being rendered.

## Text encoding

- **`perl -pi` without an encoding layer destroys UTF-8, worse than PS 5.1 does.** PS 5.1's cmdlets double-encode (recoverable); perl emitted a "Wide character in print" warning and wrote **lone `0xE2` bytes** — the first byte of each multi-byte sequence, the rest dropped. `—` and `├──` became invalid UTF-8 that no mechanical reversal can fix, and `sed` cannot even pattern-match it because the bytes are not valid characters. The file had to be rewritten by hand. Use the editor tools for text containing dashes, arrows or box-drawing.
- **The vault snapshot faithfully copies a corrupted source.** The round-trip check flagged mojibake in `README.md` and the instinct was to blame the sync script — but the *repo* file was the damaged one. Verify after any bulk text edit, and read the failure carefully before fixing the wrong end.

## Process

- **Count the silent exits before trusting a subsystem.** Her ears had **four** separate ways to lose an utterance and not one of them said so: a flag cleared before transcription finished, an empty transcript, a confidence below the floor logged at debug, and a bare `if (_responding) return;`. Any one of them alone would have been found in a day; four of them together made *"I pressed the button and nothing happened"* indistinguishable from four different faults, and the feature stayed broken for twenty-six versions. **Anywhere a person's words can be dropped, the log has to say which drop it was.** Not a warning, not an error — a sentence.
- **A comment describing behaviour is not evidence of it, and is worse than nothing when it is wrong.** `Consider` said *"push-to-talk bypasses the gate entirely, since a held button has already answered the question it asks."* It did not: every transcript reaches `OnHeard` whatever source produced it, so a held button was judged like anything overheard and *"yes"* was dropped as too short to be addressed to anyone. The comment was read as a specification for months. If a claim like that matters, it needs a check, not a paragraph.
- **A harness configured to avoid a subsystem cannot see bugs in it.** `RoomChecks` builds its session with `Gate = "off"`. It is the *only* harness that drives a face taking the floor — so the one place the gate met push-to-talk was the one place the gate was disabled. Convenient test configuration is a blind spot with a comment on it: write down what each harness has switched off, and treat that list as untested surface.
- **A constant a human worked out by hand from a format defined somewhere else will drift, and the drift is silent.** `RemoteKey` wanted "at least 24 characters" because someone counted four groups of five and three dashes and got it wrong by one. Correcting 24 to 23 would have been the same bug wearing a different number, reappearing the next time the grouping changed. **Derive it** — `Chars = Groups * GroupSize`, declared once, used by both halves — and compare the *normalised* string, so the length test and the equality test cannot disagree about which characters are the secret. Proven by setting `Groups = 5`: authentication stays green, and only the two assertions that describe the shape go red, which is what a deliberate format change should look like.
- **The assertion that catches this class is the dullest one available: write it, read it back, assert you got the same thing.** Nothing had ever compared a stored key against itself, which is exactly why a bug this total survived nine versions. One round-trip check turns "the code looks right" into "the code demonstrably preserves its own data". It is worth writing for anything that persists a value it will later need to recognise — a key, a token, a config field, an id.
- **Write the diagnostic, not the guess.** `EarsTest -- mic` (enumerate devices, mark the Windows default, read Windows' own meter) turned "can she hear me?" into a two-minute answer. Every subsystem here got a headless harness before it got trusted, and each one found a real bug on its first run.
- **A red line that does not say what to try is barely better than no line.** Every failing self-test check carries a `fix` sentence, and the microphone one names the RDP client setting by its full menu path. The value is not in detecting the fault; it is in the reader knowing what to do next.
- **A redactor that matches substrings redacts the wrong things.** `Hotkey` contains "key" and `MaxTokens` contains "token", so the first version of the bundle's config copy blanked two of the most useful lines in a fault report — including the setting behind a bug already in this file. Match whole words of the name, and only ever redact a **string**: a secret is never a number or a boolean. Over-redaction is not the safe default; it quietly destroys the thing you built the bundle to carry.
- **"Sent only when it changes" leaves a late arrival with nothing.** `emotion` is sent on change, which is right — repeating it would restart the movement towards it every sentence. But it means a face attaching mid-session is never told what she is currently wearing, and a mood can sit unchanged for many minutes. Any message with change-only semantics needs its current value in the handshake. Found by a conformance check, not by looking.
- **Write the harness before the thing it tests, when the thing is expensive.** The photoreal renderer needs a GPU that does not exist yet, but the *contract* it must be built against could be checked today — and checking it found a fault that would have looked like a bug in the renderer. The cheapest time to find a protocol gap is before anything depends on it.
- **A smaller helper model can be far slower than a bigger resident one.** A 1.7B gate beside a 3B brain looked obviously right and was the opposite: the server can only hold one, so it evicted and reloaded on *every* utterance — 24 seconds against 0.7 for a warm call. Count what is resident, not what is small.
- **A reasoning model cannot be used as a gate.** Asked a yes-or-no question with a 24-token budget, `qwen3:1.7b` spent all of it thinking and returned an empty answer. `think`, `/no_think` and `chat_template_kwargs.enable_thinking` were each ignored by the OpenAI-compatible endpoint; only the vendor's own API honoured it. Pick a non-reasoning model rather than trying to switch the reasoning off.
- **The word you choose in a prompt is a design decision.** Asking whether a line was "addressed to an assistant" made the model read *addressed* as *named*, and it discarded "tell me a short joke". Asking whether it was "a question or a request an assistant should answer" fixed it. Same intent, opposite behaviour — and prompts get reviewed far less carefully than the code around them.
- **Halving a prompt halved the latency.** Every token in a system prompt is processed on every call, and on a modest machine prompt processing dominates. Brevity in an instruction is a performance decision, not only a stylistic one.
- **A permission nobody answers is answered by somebody else.** WebView2 raises `PermissionRequested`, and with no handler the *runtime* decides — so a config switch reading `"Camera": false` was a suggestion the page could go around. Any embedded browser needs its host to answer permissions explicitly, and to deny by default: the handler is four lines and its absence is invisible.
- **"It opened and returned no error" is not "it worked" — for a camera either.** A lens cap, a privacy shutter and an unlit room are all indistinguishable from success. The fix is the same one the microphone got in Stage 4: measure what came back and say so. Describing the frame's brightness and spread cost twenty lines and immediately found a real bug.
- **Timings tuned against a synthetic device will be wrong against a real one.** Two animation frames before grabbing a still was plenty for a virtual camera and far too little for a sensor with auto-exposure to finish. Hardware has settling time that emulation does not, and no amount of reasoning would have produced the number — only a measurement did.
- **`SetForegroundWindow` fails silently from a background process,** and the click then lands on whatever window *is* in front. This wasted a debugging round looking for a bug in the app while the clicks were going into a chat window. Attach to the foreground thread's input queue first, and then **verify** the window actually came forward before clicking anything.
- **A check nobody has watched fail is not yet a check.** The face's new syntax check was written, passed on the first run, and that proved nothing at all — a check that always returns green is indistinguishable from one that cannot detect anything. The only informative run was against a deliberately broken copy, which also confirmed the *shape* of the failure was useful: it named the file and the line. Break it on purpose before believing it.
- **Fall back to the thing that needs nothing.** An undefined profile fell back to base settings, and the base brain was the hosted one — so a misspelled `--profile` produced an assistant that refused every single turn for want of an API key. The local brain needs no key, no network and no account; it is the only honest default for a fallback path. Ask what a mistyped setting lands on, because that is what a stranger's machine will land on too.
- **A silent fallback is the mechanism by which a machine runs something nobody chose.** "Profile not defined; using the base settings" was an *info* line. It had been printing truthfully for weeks. Anything that quietly substitutes one configuration for another deserves a warning that names the alternatives — the fix cost one line and would have saved the whole investigation.
- **Authentication is not authorisation, and a system with only the first will look finished.** The remote key decided *whether* a phone could connect and nothing decided *what it could then do* — so a paired handset could open this machine's microphone, change its capture device and write out a bundle of her transcripts. Every one of those paths had been reachable since the day remote access shipped. The fix is an authority table on the *sender*, checked before the switch acts; the lesson is that "can you get in" and "what may you touch" are two questions, and building the first one well is exactly what makes forgetting the second easy.
- **Hiding a control is not enforcing it.** The obvious fix for a mic button that should not exist on a phone is to hide the button. It fixes nothing: a face that can send `listen` by hand still opens the microphone. The guard belongs in the host and the hiding belongs in the renderer, and **both are needed** — without the guard the control is live, and without the hint the interface shows a button that silently does nothing, which teaches people that corner of the screen is broken.
- **Refuse out loud; a silent no-op is indistinguishable from a bug.** Everything refused here answers with a `notice` and logs once. A face that quietly does nothing looks broken, and somebody will spend an evening on it — which is the same reasoning that put `overheard` on her face rather than only in the log.
- **A singleton is a design decision that only shows up when the second one arrives.** One `Conversation`, one `_state`, one `_mood`, one `AttentionGate` — every one of them correct while she was one screen, and every one of them wrong the moment a phone was a peer. The tell is not the field itself but the **untargeted send** beside it: `Send(message)` with no recipient encodes "there is only ever one of these" in a place nobody thinks to re-read.
- **Ask what a state is a fact *about*.** The whole routing table fell out of one question asked per message. Her mood is about a conversation, so it is per room. The tempo of the music is about *this machine's speakers*, so it goes to the host room and nowhere else — the same trap that Stage 14 item 2 hit with the room microphone, wearing different clothes. Getting this wrong does not throw; it just quietly tells somebody in a gym what is playing in a house they are not in.
- **Cut at the last possible point.** Silencing her in a room she is not in was done by zeroing the buffer *after* the tap that feeds the visemes and the network stream, not by declining to speak. Anywhere earlier and her mouth, her state and the audio a phone is receiving all come apart. When you need to suppress an output, suppress the *output* — everything upstream of it is probably load-bearing for something else.
- **Absent is not empty, and conflating them breaks every old client.** A face that sends no `senses` has not told you it has no camera; it has told you nothing, because it was written before the field existed. Treating silence as a denial would have stopped `look` reaching the built-in page. Any field added to an existing protocol needs an explicit answer to "what does a client that never heard of this look like?" — and that answer is almost never the same as the empty value.
- **A test double that only speaks one dialect fails like the real thing being absent.** A forty-line stub of a model server understood `Content-Length` and `PostAsJsonAsync` sends chunked; then, once it read chunks, it left the trailing CRLF unread, which makes Windows close with an RST and the client discard a response it had already been handed. Both presented identically as "no model server at that address" — a message about the *environment*, pointing away from the bug. When a double fails, suspect the double before the diagnosis it is offering.
- **A test that waits on "any signal" waits on the wrong one.** The helper that drove a turn treated any `notice` as the end of it, so "her Windows voice cannot leave this machine" — a correct message, arriving first — ended the wait before she had said a word, and five checks failed against working code. Then it waited on the *transcript*, which is sent before the turn is actually over, so the next room was legitimately refused. Wait for the thing that means what you mean: here, the room going idle.
- **A to-do written in the present tense becomes a fact.** "The API key needs pasting into Settings" was true for about four hours after the machine move. It was pasted, the line was never ticked, and a later reader — reasonably — read it as *there is no API key on this machine*. That claim then propagated into three ROADMAP entries, held Stage 14's camera test open across four versions, and supplied half the excuse for deferring the tool loop. The whole time, `--profile cloud` would have started her on `claude-sonnet-5`. **Checklist items must be tickable and dated**, and a claim about the environment should carry the command that falsifies it: "there is no key" is unfalsifiable prose, `--profile cloud` → `brain: claude-sonnet-5` is a check.
- **An inherited blocker is a claim, not a constraint — re-test it before you build around it.** Item 9 took item 1's "no key on this machine" in good faith and wrote it into its own acceptance notes as the reason a criterion could not be walked. Nobody re-checked, because it read as a *finding*. The cost was not the wrong sentence; it was the work shaped around it. When a previous entry explains why something cannot be done, spend the two minutes proving it still cannot.
- **Two questions that share an answer today will stop sharing it.** The watch button asked "may she look at all" and used it to decide "could this renderer open a camera". Identical on the desktop, where the host's setting and a secure context are both true; wrong on a phone over plain HTTP, where the room says yes and `navigator.mediaDevices` is `undefined`. The test to distinguish them had been written nine lines away in the same file the day before and simply not reused. **Name the fact rather than the symptom** — `canOpenACamera`, not `msg.camera` — and the two stop being interchangeable by accident.
- **A control that can only fail teaches people the whole panel is broken**, and the failure is invisible to whoever shipped it: this one only threw on a face nobody here was holding. It took a handset on the far side of a LAN to produce `watch failed: Cannot read properties of undefined (reading 'getUserMedia')`. Anything gated on a capability should be gated on **that capability**, measured, not on a proxy for it that happens to correlate on the developer's machine.
- **A rule that says no to a whole class will strand something legitimate inside it.** Item 9's authority table was right, and 0.24.1's secure-context gate was right, and together they left a handset — holding a microphone and a camera, with a native client already using both — offered neither. The fix is never a hole in the rule; it is **a seam that lets the legitimate case identify itself**. `window.OctaviaEmbedder` is that seam, and a face with no embedder still gets the plain refusal.
- **Ask what the thing is running *inside*.** The page could not open a camera and could not take the floor, and both looked like protocol problems. Neither was: the floor is a `FaceId` and the panel is a different face, and the origin is not secure. The capability existed a layer out, in the app hosting the WebView — so the answer was to borrow rather than to widen the wire. A renderer that special-cases one client stops being a renderer; a renderer that asks "what am I embedded in?" does not.
- **Say the one thing you could not match, in the code, where it will be read.** The phone's microphone button is press-and-hold and the desktop's is a toggle, because always-on listening in a remote room needs echo cancellation nobody has built. Writing that in the comment rather than smoothing over it turned a vague deferred item into the *only* remaining difference between the two — which is a far sharper way to hold it.
- **A test harness that accumulates state passes for the wrong reason.** `AddScriptToExecuteOnDocumentCreated` adds; it does not replace. Without removing the previous injection, the handset's embedder was still present in the run that was supposed to prove a plain browser gets nothing — and both of those checks would have gone green while testing the opposite page. **Anything a check sets up, it must be able to tear down**, or the second scenario is not the scenario you named it.
- **Reproduce the condition rather than simulating it, and assert that you did.** The two origins in the embedder checks are real — `https://octavia.face` is a secure context and `http://octavia.face` is not — rather than `isSecureContext` being overridden. And the first assertion checks *which one it got*, so if that ever stops being true the run says so instead of quietly proving nothing.
- **When you lock a message down, list what it actually does — one of those things is usually somebody else's.** `listen` opened this machine's microphone *and* started the speech recogniser. The first is a host-room device and locking it was right; the second is being-wide, one Whisper for every room. Item 9 locked both, so a room face could never start her ears — and it stayed invisible for two versions because no remote face had a microphone button to press. **A guard is applied to a name, and a name can be hiding two jobs.**
- **A capability flag must say "will", not "has".** `micAccepted` reported whether the recogniser was already open, so it was false on every fresh session — a handset was told its microphone button could only fail, hid it correctly, and the fault presented as a client bug. Anything a client uses to decide whether to *offer* something has to describe the reachable state, not the current one.
- **Watch for a call that does more than its name, especially while fixing a permissions bug.** `UseSource` *starts* what it is given — so the obvious line, handing the ears back the local microphone when a face let go, would have opened the desk's microphone because a phone released a button. That is exactly the fault the guard exists to prevent, arriving through a door the guard did not cover. Two more in the same hour: `Start` subscribed without detaching, and an `Unmute` that only ever ran on the desk's path.
- **Rank failure modes by how legible they are, not by how often they happen.** Two faults sat side by side in the same three-second window: letting go while the model loads produces *silence*, and holding through it produces a **plausible, truncated sentence**. The second is far worse. Silence says "nothing happened, press again"; a shortened sentence says nothing at all, she answers the wrong question, and everything looks like it worked. **A wrong answer that looks right is the most expensive output a system can produce**, and it is worth spending real effort to turn one into an obvious nothing.
- **A missing acknowledgement is a design decision made by omission.** The client streams the instant it asks for the floor because there is nothing to wait for — so any latency the host adds between the request and the grant silently eats audio. If a request can take time, either say when it is granted or absorb what arrives in the meantime; leaving both out means the caller is guessing, and the guess is only right while the operation is fast.
- **A boundary you have kept honestly is a boundary you can cut along later.** Splitting her into a server and a client was six hours of mostly moving files, and the reason is that nobody had ever cheated: `OctaviaSession` had three references to a UI framework in 9,361 lines, `FaceHub` already took a nullable page, and a test harness had been running her headless for a month without anybody framing it that way. **The discipline was paid for in small refusals over twenty-five versions and collected in one afternoon.** The corollary is the useful half: if a split like this would be hard, that is not a fact about the split — it is a measurement of how much the boundary has already been violated.
- **Look for the thing that was already doing it accidentally.** Before writing a headless host, the cheapest question was "has anything ever run this without a window?" — and `RoomChecks` had, fifty assertions at a time, on every test run. That turned an unknown into a demonstration and shrank the risk of the whole stage before a line was written. A test harness is usually the first place a system gets used in a way its author did not design for.
- **Deleting a transport breaks whoever was impersonating it.** Two check suites had been pretending to be the host over `postMessage`, and removing that channel broke both — which felt like collateral damage and was actually the point: they had been testing a path production no longer had. Rewiring them onto the real socket is what *found* the rule that a reconnected face must re-announce itself. **When a test breaks because you removed something real, ask what it was really asserting; often the answer is "less than I thought".**
- **A fallback outlives the thing it was falling back to, and then it lies.** The page's `postMessage` path existed only for a WebView2 host that no longer exists. Left in, `send` would have reported success into nothing — and worse, the "lost the connection" notice was *suppressed* whenever a WebView2 host was detected, which after the split is precisely the face that needs it. **Every fallback should name the condition it exists for**, so that when the condition goes, the fallback goes with it rather than becoming a silent success.
- **Something that dies with its host never needed to reconnect.** The face opened one socket and never retried, and that was correct for as long as a dead socket meant a dead application. The moment the host became a separate process, the same code meant every face went dark permanently with nothing on screen. **Ask what a component's lifetime is coupled to, and re-ask it whenever the process boundary moves.**
- **Enforce architectural rules where they are written, not where they are compiled.** Three assemblies that see each other's internals cannot express "the client must not construct a session" in the type system. Checking the *source text* is blunt and exactly right — and it went red on purpose four times before it was believed. The rules that decay silently are the ones no tool is watching.
- **An argument that stops being understood is not an error, it is silence.** The desktop shortcut had passed `--profile dev` to `Octavia.exe` for weeks. After the split that exe was a client, which does not parse `--profile` at all — so the icon opened a window with no server to attach to and nothing anywhere said why. **Shortcuts, scheduled tasks and service definitions are where stale arguments go to be un-re-read**, because they live outside the repo and no build touches them. Anything outside the tree that names a flag should be regenerated by something inside it.
- **Check whether the feature you picked does the job at the *time* you need it.** Stage 8's animation source was chosen on one reading of a feature list: Epic's Audio-Driven Animation is vendor-neutral, built into the renderer, and needs no second inference stack — all true, and all beside the point, because it is an **offline** editor workflow that bakes a sequence from an audio asset. Octavia needs sentences animated as she speaks them. Epic's own documentation draws the line in a single sentence, and the live path is a *different feature* with a different name. **"Does it do X" and "does it do X in real time, from a stream, at runtime" are different questions**, and a capability table has no column for the second one. This is the third time a plausible option was written down as a finding after one reading; the previous two are above.
- **When a rule produces a special case, check whether deleting the special case is cheaper than generalising it.** The host room was going to become "the client lends the server its devices" — a privileged face, a new capability list, a routing table. The owner's rule was simpler and better: *the server holds no device at all, and the Windows client does exactly what the phone does*. That needs no new concept, because `talking`, `sight` and the floor already are how a face lends a device. **The desktop had been special since v0.1.0 and nobody had asked whether it needed to be.**
- **A fault that needs a mechanism to survive it is often a fault that should not be reachable.** Item 11 — the first press of a cold session losing its opening words — had two designed fixes, and both were about *surviving* a three-second gap: buffer the frames, or acknowledge the request. Opening the models at startup, where nobody is talking, means there is no gap. **It arrived as a convenience request** (*"the ears should auto start"*), which is the second time that has happened; when someone asks for something to happen earlier, check whether a logged bug lives in the interval they are removing.
- **A model has no present tense, and will not tell you so.** Asked the date, she answered from her training data: months stale, stated with complete confidence, and indistinguishable from a correct answer. **The host knows things the model cannot** — the clock, the devices, what is playing — and anything in that category has to be *handed over* rather than hoped for. The corollary is that a model handed the answer may still recite its disclaimer, so the instruction to use it has to be explicit.
- **Check the exit path of anything you have just given more to hold.** The server had run eight times and shut down cleanly zero times, and nothing said so — `Console.CancelKeyPress` covers Ctrl+C and Ctrl+Break, and closing the console window is neither. It went unnoticed while the process was cheap and became worth fixing the moment the same process held 1.6 GB of speech model and a set of MCP child processes. **The absence of a "stopped" line is evidence**, and it was sitting in the log the whole time.
- **Scoping a singleton before you need to is cheap; discovering you needed to is not** — the converse of the lesson above, and it paid out. Item 7 gave every room its own `AttentionGate` with no shared statics, and the note recording it said the gate "only bites when a room gets always-on listening, which on Android it does not have and is not getting here". Eight days later item 6 gave a room exactly that, and the gate needed **no work at all** to become load-bearing. The cost of scoping it early was a constructor argument; the cost of not would have been finding out through a phone being judged by the desktop's gate.
- **Two people solving different problems reaching the same shape is the strongest evidence you get.** The owner's rule — *the server holds no device; every client passes its own up* — and item 6's echo fix landing **on the client** were decided hours apart, by different hands, for unrelated reasons: one as a principle about where hardware belongs, the other because the host simply cannot know when a remote speaker fell silent. Neither knew about the other. When a constraint and an implementation converge like that without coordination, stop looking for a third option.
- **A note that another item blocks yours can go stale before you act on it.** Yesterday's roadmap said item 6 was now a *prerequisite* for Stage 15 item 3, and the reasoning was sound; item 6 shipped that afternoon and the dependency inverted — item 3 inherits a solved problem instead of creating one. The claim was fine, and being stale is not the same as having been wrong. **What matters is that a blocking claim gets re-read when the thing it names moves** — the same discipline as *"an inherited blocker is a claim, not a constraint"* above, pointed the other way through time.
- **A self-test that spends money is a bad self-test.** The brain check pings a local endpoint and, for Claude, verifies only that a key is stored — it never makes a call. Anything a worried user might press repeatedly has to be free.
- **A retry that lives inside the thing it retries cannot recover a cold start.** The page reconnects with backoff when her server goes away — genuinely good, and structurally incapable of covering the case where the server was never there, because the retry code has to be downloaded from the missing thing first. It looked like reconnection was handled; what was handled was *half* of it, and the half nobody tests is the one where you double-click an icon on a machine that has just booted. **"Server goes away" and "server was never there" are different faults**, and a mechanism that reads as covering both should be asked which one it actually observes.
- **Three ways to stop a console process, and two of them lie.** `CloseMainWindow` returns true and the process is gone in six seconds *with its shutdown handler never run* — nothing logged, resources released by the OS rather than by the program. Ctrl+C is accepted and ignored: both API calls return true and the server keeps serving. Only Ctrl+Break works, and it **cannot be survived by whoever raises it** — `SetConsoleCtrlHandler(NULL, TRUE)` ignores Ctrl+C only, and a real handler returning true did not save the caller either. The general lesson is not about Win32: **an API returning success is a claim about the call, not about the outcome you wanted.** The log line was the only thing that could tell them apart, and it was the thing being tested for.
- **A fix that only works after `dotnet publish` is a fix nobody exercises.** "The server sits beside the client" is true of `dist` and never true of a working tree, where every project has its own `bin`. Written the obvious way, the new start path would have been correct in the shipped layout and dead in the only layout it gets run in during development — which is precisely how the original failure shipped. **Make the convenience work in the layout you actually type in**, or it will be verified once, by hand, on the day it was written.
- **Do not let a stated constraint become an assumption in the code.** *"The server and the client will always share a box"* was offered as the current arrangement and taken as a licence to call the Windows Service unnecessary. The owner's correction was immediate and right — *"it may not always be the case"* — and it is the same mistake this project has a whole roadmap item about: **item 3 exists to stop the code believing in a deployment.** A constraint tells you what you may skip *today*; it is not a statement about what will always be true, and the difference is invisible right up until somebody moves a machine.
- **An error produced before the question is understood tells you nothing about the question.** A `401` on the UniFi integration endpoint was read as proof the API existed and was merely locked; a deliberately nonsensical path under the same prefix returned `401` too, because the reverse proxy authenticates before it routes. The probe was measuring the proxy, not the API. **Any check whose "failure" looks identical for a wrong answer and a wrong question is not a check** — the fix was a control: ask for something that certainly does not exist, and see whether the answer changes.
- **Look at what the infrastructure already knows before integrating anything.** Presence was scoped as a camera problem in Stage 9 and a Home Assistant problem in Stage 12. The router had a named list of eighteen devices the whole time — *Kitchen - Plug - Microwave*, connected 36 days — so "is anyone home" and "is the freezer still running" became answerable with no smart-home integration in existence. **The network layer knows about the physical world**, and it is usually the integration nobody costed because it is not marketed as one.
- **When safety depends on wording rather than on code, assert the wording.** The tool risk heuristic reads names and descriptions, so five deliberately read-only tools are classified safe *because of how their descriptions are phrased*. Someone adding "after a restart" to a status tool's description would silently turn a free query into one she stops to ask permission for, and no compiler, type or test would have noticed. The check asserts the classification rather than the text, so it survives rewording — and it went red on demand before it was believed.
- **The expensive design is sometimes the one that keeps the product's whole point.** The tool loop could have used a cheap non-streaming request to find out whether tools were wanted, then streamed the final answer. It would have been half the code and it would have silently thrown away *"Let me check that for you"* — the sentence she speaks **before** the call goes out, while the gateway is being queried. She streams so the voice can start early; a design that stops streaming during the slowest part of a turn defeats the reason streaming exists. **Ask what a mechanism is for before optimising the case that skips it.**
- **State the half you did not build, in the code, at the call site.** The tool loop always passes `confirmed: false`, so a dangerous tool can never run — safe, and *incomplete*. Written without a comment it reads as finished, and the next person to touch it has no way to tell a deliberate safe default from an oversight. The gap is named where the argument is passed, not only in a roadmap nobody has open. **An unbuilt half that looks built is worse than one that fails loudly**, and this is the half where a door gets unlocked.
- **Guard the loop that cannot end itself.** A model answering its own tool result with another tool call is a failure with no natural stopping point: every lap costs money and nothing times out. A slow answer eventually arrives; this one does not. The ceiling is four rounds and it *logs when it bites*, because a turn that stopped at a limit looks exactly like a turn that simply finished.
- **Prove it against the real thing, then keep that proof out of the suite.** The tool loop is verified by asking two real questions of a paid model and a real gateway — the only way to know the model actually *chooses* a tool rather than that the plumbing compiles. That probe is deliberately not in the default run: it spends money every time, and this project already learnt that anything a worried person might press repeatedly has to be free. Everything up to the last hop stays covered for nothing.
- **"It works" and "it works on the configuration you actually run" are different claims.** The tool loop shipped against Claude and was true; the `home` profile is a local brain, so on the profile she is started under every day she still could not call a tool. The feature was announced complete while the path anyone would actually take was untouched. **Check which code path the default configuration takes before calling a capability delivered** — the demo profile and the daily profile are rarely the same one, and the gap is invisible from inside the demo.
- **Write against the format, not against the one server that happens to be running.** Ollama returns a streamed tool call whole, in a single chunk, with its id, name and arguments complete — so the naive reading works perfectly and would break on llama-server or LM Studio, which are free to fragment the arguments across many chunks and to send the id only in the first. The OpenAI streaming shape says the *index* identifies a call across chunks, not the id. Accumulating every field costs nothing when there is one fragment and is the only correct thing when there are twenty; testing against one implementation would never have shown the difference.
- **An exact tool result does not make an exact answer.** Asked about the network hardware, a 7B model reported the two devices correctly and added *"with their firmware versions up to date"* — which no tool said and nothing checked. The loop was working perfectly; the embellishment is downstream of it. **The reliability of a tool call is not the reliability of the sentence built from it**, which is an argument for keeping anything dangerous behind explicit confirmation no matter how good the plumbing gets.
- **Read back what you told the system to store, not what you told it.** `sc create` reported success and the service worked; the `ImagePath` it had actually written was **missing the quotes around the exe**, because the command was built as one string and two layers of parsing disagreed about them. Under `C:\Projects` that is invisible. Under `C:\Program Files` it is the classic unquoted-service-path failure — Windows resolves `C:\Program.exe` and the service never starts, on the one machine you cannot debug. The registry value was read back and the quotes were not there. **A configuration API's success means the call was accepted, not that it stored what you meant**; where an API takes a command line, hand it an argument list and let the runtime escape it once.
- **When a capability needs elevation, spend the elevation once rather than every time.** A Windows service is an administrator's object, so the obvious build makes every start and stop raise a UAC prompt — between somebody and their own companion, forever. One `sdset` at install grants that account start/stop on that one service and the prompt is gone permanently. **The question is not "does this need admin" but "how many times".** Grant narrowly while you are there: start, stop, pause and query, but never the right to hand other people control.
- **The platform mechanism did in one call what three hand-rolled ones could not.** Stopping the console server cleanly from outside was measured failing three ways — `CloseMainWindow` skipped the unwind, Ctrl+C was ignored, Ctrl+Break killed the caller. The service control manager produced the clean shutdown line on the first attempt, because stopping a service is a thing Windows is *designed* to do and closing somebody's console window is not. **Effort spent making a mechanism do something adjacent to its purpose is usually a sign the right mechanism is elsewhere** — and here the failed attempts were what made the case for building this.
- **Say the awkward consequence at the moment of the change, not in a document.** A service runs as LocalSystem and her API key is DPAPI-sealed to a user account, so the hosted brain silently has no key — a failure that presents as a broken brain rather than as a permissions problem. `--install` prints it, with both fixes, at the one moment somebody is definitely looking. A README nobody re-reads is where this kind of note goes to be missed.
- **A default stated as a constraint becomes a limitation nobody revisits.** *"A service runs as LocalSystem, so the hosted brain cannot read her key"* was written as a fact about services. It is a fact about the **default**, and the owner disproved it within the hour by setting the service to log on as himself — after which the key decrypted, the audio devices enumerated and her voice played, all from session 0. Nothing was wrong except the confidence. **Write down which part of an obstacle is the mechanism and which part is merely the setting you happened to use**, because the second kind gets fixed in a minute by anyone who thinks to try, and never gets tried if the note says it cannot be done.
